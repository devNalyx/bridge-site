Connecting a repo_

A concrete look at what actually happens when a repository starts working with Bridge — not marketing copy, the real process used for every repo Bridge currently coordinates.

One fact worth knowing up front: a single running Bridge instance already supports multiple repositories at once. Adding a repo isn't new infrastructure or a code change — it's routing configuration, applied to a system that's already running.

The process

  1. Install, scoped narrowly. Bridge connects the same way any GitHub App does — installed on the specific repository, not the whole account, with the minimum permissions it actually needs (contents: read, pull requests and issues: read/write) and subscribed only to the events it reacts to (pull request activity, reviews, issue comments).
  2. Routing and roles, decided up front. Each repo gets its own subscriptions: which roles — implementer, reviewer, security reviewer, tester, human approver — are watching it, and under what policy they're allowed to act.
  3. Conservative by default. A repo Bridge hasn't worked with before starts with no auto-approval rules at all. Every decision that matters goes to a human until the system has demonstrated, on that repo specifically, that it behaves correctly.
  4. Watched, not assumed. The first real pull requests get read closely — does the routing look right, does the context handed between participants make sense, does the audit trail read the way it should. Trust in a new repo is earned by watching it work, not granted the moment the install finishes.

Why it's a process, not a button

This is also why early access starts as a conversation rather than a self-serve signup — connecting a new repo is a deliberate, watched step, the same one used internally, not a black box turned on for anyone who asks.
